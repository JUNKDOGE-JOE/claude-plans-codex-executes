# 任务简报模板

简报是 worker 唯一能看到的东西——它看不到你的会话、记忆、也看不到主检出里未跟踪的文件。**产出质量基本由简报决定。** 写到 `.codex/brief.md`（worktree 则写到 `<worktree>/.codex/brief.md`），用 `-BriefFile` 传给 `codex-run.ps1`。

## 标准模板（五段，缺一不可）

```markdown
## 任务
<一句话说清要做什么；用户可见的结果是什么>

## 背景与相关文件
- <具体路径>：<它现在怎么做、要照哪个模式写>
- <具体路径>：<…>
- 仓库规则（原文嵌入，worker 看不到仓库的 CLAUDE.md 之外的会话约定）：
  - <例如：新增持久字段必须先开 ADR；证据政策；禁止 cepRequire('os'|'path')；CHANGELOG 用 `### Unreleased` 不带方括号>
- 注释：使用 Codex 技能 `$comment-discipline`——只写意图、不变量、平台陷阱；不写 AI / 评审 / 阶段痕迹。

## 约束
- 遵循现有代码风格与本地 helper API；不引入新依赖（需要就停下来说明）。
- 不改动无关代码 / 无关文件。**不要动**：<文件清单——fanout 时这是三路 diff 不相撞的保证>
- **不要 commit**（由编排者提交）。
- <其他：平台、兼容版本、性能上限…>

## 验收标准
- <可验证的产出 1>
- <可验证的产出 2>
- 跑这些测试并通过：`<精确命令>`

## 完成后
总结你改了哪些文件、为什么、如何验证（跑了什么、结果如何；跑不了的如实写「未运行」，不要写「应该能过」）。
```

## 推荐加强项（来自 2026-07 的受控实验，真的挡过事故）

在 `## 约束` 里多加两段，任务越大越值得：

```markdown
### 非目标（NON-GOALS）
- <明确不做的 3–5 件事；通常每条都对应一次具体的历史翻车>

### 遇到以下情况停下来报告，不要自行决定（STOP-AND-ASK）
- 简报对代码 / SDK / 产品的描述与实际不符
- 需要删除或归档你不确定来源的文件 / 分支 / worktree
- 需要新增依赖、改公共接口、动构建或发布脚本
- <任务特定条件>
```

停下来报告是成功不是失败：历史上多次是简报写错了，worker 停下来才暴露出来；一个「尽力而为」的 worker 会把错的事做完并报告成功。

## 写简报时的自检

- [ ] 只看简报，一个没见过这个仓库的人能开工吗？
- [ ] 每条验收标准都能被命令或 diff 证明吗？
- [ ] 「不要动」清单写了吗？fanout 的三份简报两两不重叠吗？
- [ ] 仓库级规则（ADR / 证据 / 门禁测试 / 命名）嵌进去了吗？
- [ ] worktree 里缺的东西（计划文档、设计导出、node_modules 的替代说明）放进 `<worktree>/.codex/` 了吗？
- [ ] 明确写了「不要 commit」吗？
